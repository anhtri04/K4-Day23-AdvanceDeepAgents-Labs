# LLM Agents and Tool Use: A Survey of Architectures, Interfaces, Training, Evaluation and Security

## TL;DR

- Tool-using LLM agents have converged on a small set of control-loop motifs — interleaved reason–act ([1]), verbal self-critique ([2]), explicit plan/search ([3][4]), and tool-augmented training ([5]) — which practitioners now organise along an explicit workflow-versus-agent autonomy spectrum rather than as competing methods ([6][7]).
- The interface layer has moved from in-conversation JSON-Schema function calling ([8][9]) to protocol-mediated tool servers (MCP) with dynamic discovery ([10][11]), and the binding constraint is now payload size, not model capability: multi-server setups can spend tens of thousands of tokens per turn on tool definitions alone ([12][13]).
- Post-training for tool use follows a consistent two-stage recipe — cold-start SFT on synthetic trajectories, then RL with verifiable outcome rewards ([14][15]) — delivering large reported gains (67% AIME in 400 steps vs 40% for text-only RL at 1080 steps; +41% over RAG for Search-R1 at 7B) ([14][16]), though dense per-turn rewards can reduce performance by up to 14 points ([17]).
- Evaluation has bifurcated into call-correctness leaderboards ([18][19][20]) and execution-graded live environments ([21][22][23][24]), with reliability metrics such as pass^k exposing that a 69.2% pass@1 collapses to 46.2% pass^4 ([25]); benchmark validity is now an active critique literature ([26][27][28]).
- Security is the field's hardest open problem: indirect prompt injection through tool output is structurally enabled by the "lethal trifecta" ([29][30]), adaptive attacks bypass 12 published defences at over 90% success ([31]), and error compounding plus token blow-up make long-horizon agents unreliable and expensive ([32][33]).

## Background

An LLM agent, in the sense this survey uses, is a language model that is given a set of tools and the ability to decide, in a loop, which to invoke, with what arguments, and how to use the returned observations. The concept crystallised with ReAct, which interleaved reasoning traces with task-specific actions so the model could both plan and ground itself against external sources; ReAct beat imitation and RL baselines by 34% absolute success on ALFWorld and 10% on WebShop using only one or two in-context examples ([1]). In parallel, Toolformer showed a model could teach itself when and how to call APIs (calculator, QA, search, translation, calendar) from a handful of demonstrations and still improve zero-shot performance without losing language-modelling ability ([5]). Within roughly two years the area produced its own survey literature: a unified framework for LLM-based autonomous agents ([7]), a review of LLMs as agents and tool users built from 2023–2025 A*/A-conference and Q1-journal papers that evaluates 68 public datasets ([34]), and taxonomies that position agentic design patterns — reflection, planning, tool use, multi-agent collaboration — as the successor to static RAG pipelines ([35]).

Why now. Three things changed simultaneously. First, interfaces standardised: providers expose tool calling as a first-class API primitive, and MCP turned tool integration into an external, discoverable contract ([8][10][11]). Second, post-training caught up, so tool use became a learned policy rather than a prompt scaffold ([36][14][16]). Third, agents were let loose in environments where success is machine-checkable — repositories, operating systems, terminals, websites — which made progress measurable, and made the failure modes expensive and concrete ([21][22][24]). The result is a field whose bottleneck has shifted from "can the model call a tool?" to "can the system be made reliable, affordable and safe when it does?" — a framing echoed by evaluation surveys that name cost-efficiency, safety and robustness as the largest unaddressed gaps ([37]).

## Architectures: from prompting scaffolds to learned tool policies

The foundational paradigms differ less in their components than in **where the control loop lives and whether it learns**. ReAct is prompt-only: the model emits alternating thought/action/observation text, observations ground the next thought, and no weights change; the mechanism's value is failure recovery and exception handling rather than task decomposition ([1]). Toolformer relocates tool use into training — a self-supervised filter keeps only API calls that improve next-token prediction — producing a frozen capability baked into weights ([5]). Reflexion keeps the model frozen but adds episodic memory of verbal self-critiques, consuming either scalar or free-form feedback, and reported 91% pass@1 on HumanEval against GPT-4's 80% ([2]). Plan-and-Solve separates "devise a plan" from "carry out the plan" inside one prompt to attack missing-step errors, evaluated on ten datasets across three reasoning problems with GPT-3 ([3]), while Tree of Thoughts generalises this to explicit search with self-evaluation, lookahead and backtracking, lifting Game-of-24 success from 4% (CoT) to 74% ([4]). Memory-centric designs extend the same logic over long horizons: Generative Agents store a natural-language experience stream, synthesise higher-level reflections, retrieve them to plan, and the ablation shows observation, planning and reflection each contribute critically — with 25 agents coordinating a party in a sandbox town ([38]).

Three higher-level framings organise these primitives. Anthropic's engineering account draws the cleanest line: an "augmented LLM" (retrieval, tools, memory) can be wrapped in **workflows** — predefined code paths — or allowed to direct its own process as an **agent**, and it enumerates five canonical workflow shapes (prompt chaining, routing, parallelization, orchestrator-workers, evaluator-optimizer, the last being software reflexion) ([6]). The Agentic RAG survey proposes orthogonal axes — agent cardinality, control structure, autonomy, knowledge representation — to classify architectures that go beyond static RAG, which it says "lack the adaptability required for multi-step reasoning" ([35]). Multi-agent work pushes coordination furthest and identifies the characteristic pathology: denser coordination amplifies error propagation across agents and rounds, producing failures that are hard to attribute and rarely convert into structural self-improvement, a dynamic it frames as a four-stage LIFE progression ([39]).

The disagreement worth flagging is the workflow/agent boundary. Anthropic's guidance is explicitly to start simple, noting that for many applications optimising a single LLM call with retrieval and in-context examples suffices ([6]) — i.e. much of what is marketed as agency is deterministic orchestration. Conversely, the tool-augmentation literature argues that scaling the tool inventory forces genuine autonomy: ToolLLM covers 16,464 RESTful APIs across 49 categories and needs DFS-based decision-tree search over reasoning traces to generate training data, with multi-tool instructions requiring 6.76–8.24 tools on average ([20]). The two positions are reconcilable but rarely reconciled: autonomy is a cost paid to handle combinatorial tool and task spaces, not a virtue in itself.

## Interfaces and protocols: schema-calling, MCP, and the tools tax

At the API level, tool calling is an in-conversation mechanism. Anthropic's API returns a `tool_use` block with `stop_reason: "tool_use"`, has the application execute *client tools* and return a `tool_result`, and distinguishes *server tools* (web search, code execution) that run on the provider's infrastructure; `tool_choice: auto` is the default and `strict: true` guarantees schema conformance ([8]). OpenAI's equivalent defines functions with JSON Schema and offers Structured Outputs whose strict mode requires every property to appear in `required`, mandates `additionalProperties: false`, and forbids `$ref`/recursive schemas ([9]). Both apply grammar-based constrained decoding so emitted arguments are schema-exact — function calling is "about action routing" while structured outputs constrain the final response, and the two can be combined in one request ([40]).

MCP generalises this into a protocol. It is an open standard for connecting AI applications to external systems, described as "a USB-C port for AI applications" ([10]), with a host/client/server architecture where a host creates one client per server, local servers speak STDIO and remote ones Streamable HTTP, over a data layer of JSON-RPC 2.0 that exposes three primitives — tools, resources and prompts — discoverable via `*/list` and invokable via `tools/call` ([11]). The protocol is documented as stateless, with each request carrying its protocol version and capabilities in a `_meta` field and servers advertising support via `server/discover` ([11]) — although secondary explainers describe it as stateful because of the connection lifecycle and list-changed notifications, a genuine framing disagreement across sources. The economic claim for MCP is N×M collapse: one contract replaces per-product connectors ([11]).

Two orthogonal design layers shape real performance. The first is the **agent-computer interface**: SWE-agent's argument is that action space, observation format, history management and guardrails should be designed for the model rather than inherited from human shells, and interface design alone reached 12.5% pass@1 on SWE-bench and 87.7% on HumanEvalFix ([41]). The second is **tool proliferation**. ToolRet shows that off-the-shelf retrieval models perform poorly on a corpus of 43k tools across 7.6k retrieval tasks, and that weak retrieval depresses task pass rates ([13]). ScaleMCP pairs MCP servers with a retriever, CRUD-synchronised tool storage and a weighted-average embedding strategy, evaluated over 5,000 simulated financial MCP servers with 10 LLMs, 5 embedding models and 5 retriever types ([42]). The "MCP/Tools Tax" names the underlying cost: eager per-turn schema injection, practitioner-reported at roughly 10k–60k tokens per turn, which the Tool Attention middleware cuts by 95.0% (47.3k → 2.4k) and which raises simulated context utilisation from 24% to 91% — though the paper itself labels the end-to-end task, latency and cost figures as projections rather than live measurements ([12]). Anthropic's complementary guidance is to prefer few high-leverage, namespaced tools, return meaningful context instead of opaque identifiers, and expose a `response_format` enum, with one example Slack thread shrinking from 206 to 72 tokens ([43]). Orchestration frameworks occupy the layer above: LangGraph binds `@tool`-decorated callables to a chat model, receives a `tool_calls` message, executes it in a ToolNode and writes `ToolMessage`s back — the LLM never runs the tool itself ([44]). The unresolved question is whether retrieval or progressive/lazy schema loading wins; no head-to-head comparison appears in the sources surveyed ([13][42][12]).

## Training and post-training: the SFT-then-RL recipe and its contested rewards

The dominant recipe is two-stage. A cold-start SFT phase on curated or synthetic tool-use trajectories installs format and basic calling behaviour — ReTool generates code-augmented long-form reasoning traces for this purpose ([14]), Tool-Star uses tool-integrated prompting plus hint-based sampling with quality normalisation and difficulty classification ([15]) — and RL on top, usually GRPO variants, optimises from outcome feedback.

Reported results are large and consistent in direction. ReTool's 32B model reaches 67% on AIME in 400 training steps where a text-based RL baseline reaches 40% at 1080 steps, and 72.5% in extended settings, and it reports emergent code self-correction ([14]); its project page lists AIME 2024 67.0% and AIME 2025 49.3% on Qwen2.5-32B-Instruct ([14]). Search-R1 trains multi-turn query generation with retrieved-token masking for stability and a simple outcome reward, gaining 41% (Qwen2.5-7B) and 20% (Qwen2.5-3B) over RAG baselines across seven QA datasets ([16]). SWE-RL scales rule-based rewards over open-source software evolution, with Llama3-SWE-RL-70B at a 41.0% solve rate on SWE-bench Verified ([45]). ToolRL is the explicit reward-design study — reward types, scales, granularity and temporal dynamics — reporting +17% over base and +15% over SFT models, and arguing that SFT alone generalises poorly to unfamiliar tools while coarse answer-matching feedback lacks the granularity multi-parameter calls need ([36]).

What the comparisons reveal is that reward *shape* matters more than reward *existence*, and that designers disagree about dense signals. The multi-turn tool-calling work (MT-GRPO + GTPO with iterative reward calibration) finds that naively designed dense per-turn rewards degrade performance by up to 14 percentage points because reward discriminativeness and advantage direction misalign, while its calibrated variant lifts Qwen3.5-4B from 63.8% to 66.7% and Qwen3-30B-A3B from 58.0% to 69.5% on tau-bench airline ([17]). A separate empirical study of reasoning–search agents finds format rewards help, intermediate retrieval rewards have limited impact, and both model scale/initialisation and the choice of search engine materially change outcomes ([46]). Meanwhile "SFT Memorizes, RL Generalizes" argues RL with outcome rewards generalises across rule-based textual and visual variants where SFT memorises — but that SFT remains essential because it stabilises output format ([47]). Read together: SFT buys format, RL buys generalisation, and dense intermediate rewards are the least reliable lever.

Infrastructure is itself becoming a contribution. VerlTool formalises agentic RL with tool use as multi-turn trajectories with multi-modal observation tokens, contrasting it with single-turn RLVR, and reports near-2× rollout speedup across six domains ([48]). EnvFactory auto-generates verifiable, stateful executable environments and natural multi-turn trajectories, arguing that over-specified synthetic data resembles instruction sequences rather than human intent; with 85 environments across 7 domains and 2,575 trajectories it reports up to +15% BFCLv3, +8.6% MCP-Atlas and +6% on tau2-Bench/VitaBench ([49]). A third line sidesteps reward signals entirely, using agent-generated interaction data as a bridge between imitation and RL ([50]). Contamination is the standing caveat: SWE-rebench found DeepSeek-V3 at 39.7% on SWE-bench Verified versus 21.3% on decontaminated fresh tasks (an 18.4pp gap), and a survey of contamination argues static benchmarks grow more vulnerable as training corpora grow while dynamic evaluation brings its own reproducibility problems ([51][52]).

## Evaluating agents: two metric cultures and a validity crisis

Evaluation splits into two cultures. **Call-correctness leaderboards** grade the emitted tool call: BFCL, now at V4, calls itself the first comprehensive executable function-call evaluation, using AST-match since v1, adding enterprise tools in v2, multi-turn interactions in v3 and agentic evaluation in v4, and reporting overall accuracy plus per-model cost (USD) and latency ([18]). ToolBench/ToolLLM grades 16,464 APIs via ToolEval's Pass Rate and Win Rate, with the automatic evaluator correlating 75.8% with human annotators ([20]). API-Bank tests three graded abilities — Call, Retrieval+Call, Plan+Retrieval+Call — over 73 tools, 314 annotated dialogues and 753 API calls ([19]). These are cheap and reproducible but measure the call, not the task.

**Execution-graded environments** measure the outcome. SWE-bench draws 2,294 problems from 12 Python repositories ([53]); the Verified subset is 500 human-filtered instances ([21][28]), created after OpenAI screened 1,699 samples with 93 professional developers and excluded 68.3%, citing 38.3% underspecified statements and 61.1% unfair unit tests ([28]). OSWorld runs 369 real-computer tasks across 9 applications on Ubuntu/Windows/macOS, where the best agent reached 12.24% against human performance above 72% ([22]). WebArena's 812 tasks are scored by execution-based functional success against end state ([23]); Mind2Web contributes over 2,000 tasks from 137 websites and Online-Mind2Web converts it into a 300-task live benchmark across 136 websites ([54][55]). Terminal-Bench 2.0 packs 89 terminal tasks with ~3 reviewer-hours of auditing each, requires a hidden pytest suite to pass with no LLM judge and no partial credit, and saw frontier models below 65% ([24]); version 2.1 fixes issues in 28 of the 89 tasks, with reported per-pair deltas such as 58.0% → 70.1% ([56]). TheAgentCompany simulates a small software company and evaluates on 175 tasks ([57]). GAIA grades 466 questions by exact match against one answer — humans ~92% versus GPT-4 with plugins ~15% at release, most scores using the 165-question public validation set ([58]) — while MLE-bench grades 75 Kaggle competitions, where o1-preview with AIDE scaffolding reached a bronze-medal level in 16.9% ([59]).

Multi-turn reliability is where the two cultures diverge most sharply. tau-bench introduced agent–tool–user interaction with pass^k, the probability all k i.i.d. trials succeed; because pass^k = p^k, a 90% pass@1 model retains roughly 57% consistency at k=8, and Claude 3.5 Sonnet's 69.2% pass@1 on retail fell to 46.2% pass^4, with airline 46.0% → 22.5% ([25]). tau2-bench formalises "dual control" as a Dec-POMDP in which the simulated user also invokes tools against shared state, and separates reasoning errors from communication errors ([60]). Cost is tracked in BFCL's cost and latency columns ([18]) and SWE-bench's average dollars per submission ([21]), and OSWorld-Human builds human trajectories for all 369 tasks as an efficiency baseline, treating latency as a distinct axis from success ([61]).

That bifurcation is now under sustained attack on validity. "Establishing Best Practices for Building Rigorous Agentic Benchmarks" reports that SWE-bench Verified uses insufficient test cases and that tau-bench "counts empty responses as successful," with such flaws causing up to 100% relative over- or under-estimation, and its Agentic Benchmark Checklist cut overestimation on CVE-Bench by 33% ([26]). An audit of 254 SWE-bench submissions found the top ten Verified entries share 285 successes and 51 failures, leaving only 164 of 500 instances that distinguish any outcome, and exact paired McNemar tests separated none of the 29 adjacent top-thirty pairs at alpha 0.05 ([27]). A contiguity of worked examples points the same way: models identify the buggy file at 76% on Verified versus 53% on unseen repositories given only the issue text, and a further study reports ~3× higher resolution rates on Verified than on decontaminated siblings ([27]). Enterprise reporting describes real-world success typically a third to half of leaderboard figures, with a 37% lab-versus-deployment gap and a 7-point swing for the same model under different orchestration ([62]). The evaluation survey literature had already flagged the gap in cost-efficiency, safety and robustness measurement ([37]).

## Safety, security and reliability: the structural limits of current agents

**Indirect prompt injection is the defining vulnerability.** An agent that combines access to private data, exposure to untrusted content, and an external communication channel can be tricked into exfiltration — Willison's "lethal trifecta," noting that MCP encourages users to assemble exactly that combination ([29]) — and Meta's Rule of Two generalises it into a design constraint: never combine more than two of untrusted input, sensitive access, and state change without a fresh session or human supervision ([31]). The mechanism is that models cannot reliably distinguish instructions by origin, so guardrail products claiming ~95% attack capture are described as failing web-security standards ([29]). AgentDojo provides the reference harness with 97 realistic tasks across email, banking and travel and 629 security test cases, showing state-of-the-art LLMs fail many tasks even unattacked ([63]).

Concrete breakages are documented, not hypothetical. GitHub's official MCP server combined private-repo access with malicious-instruction exposure and public egress: one malicious issue comment made Claude Desktop route private repository information and personal details into a public pull request ([64]). Copilot CVE-2025-53773 let a prompt injection write `"chat.tools.autoApprove": true` into settings.json, disabling confirmations and enabling shell execution for remote code execution ([65]). SpAIware used indirect injection from web or document content to write a persistent instruction into ChatGPT's long-term memory, repeatedly exfiltrating subsequent session content via rendered image URLs until the memory was removed ([66]). MCP adds protocol-specific surfaces: tool-description poisoning, where hidden instructions ride inside a tool `description` and need only be loaded, not called ([67]); rug pulls, where a server silently mutates an approved tool ([68]); and line jumping, where payloads sit in `tools/list` output before any invocation, invisible to human approval prompts and per-call logging ([69]). Skill-file attacks generalise the pattern: SkillInject contains 202 injection-task pairs and reports up to 80% attack success on frontier models, often executing exfiltration and destructive behaviour ([70]).

**Defences trade utility for structure, and model-level defences test badly.** Design-pattern work proposes provable-resistance architectures — Action-Selector, Plan-Then-Execute, Dual-LLM, Code-Then-Execute, Context-Minimization — on the principle that once an agent ingests untrusted input it must be impossible for that input to trigger consequential actions, and concedes that reliable guarantees may be out of reach with current-generation LLMs ([71]). CaMeL builds a system layer that extracts control and data flow from the trusted query with capabilities on values; its HF abstract reports 67% secure task completion on AgentDojo while a secondary write-up cites 77% against an 84% undefended baseline — a discrepancy worth treating as two different reported numbers ([72]). Independent AgentDojo reproductions found two candidate defences had no measurable effect, while simple abort reached 0.0% attack success at a substantial utility cost (0.250 vs 0.410) ([73]). The decisive methodological result is adaptive attack: 12 published prompt-injection and jailbreak defences, each originally reporting near-zero ASR, were bypassed at above 90% when attacks were tuned against them — prompting-based defences reaching 95–99% ASR and training-based 96–100% ([31]).

**Reliability and cost compound multiplicatively.** If per-step success is p over n steps, overall success is p^n: 85% per step over 8 steps yields 27.2%, 95% over 20 steps yields 35.8%, and a 76% pass@1 can collapse to 27% on an eight-step workflow, while most pass@1 benchmarks measure only one to three steps ([32]). Token consumption compounds because full history is resent each step: agentic coding sessions can reach 500K–1M input tokens, roughly $7–15 per task at frontier pricing, with agentic workloads using ~5–30× more tokens than chat and a 20-tool-call task approaching ~200× ([33]). Hallucinated arguments are a distinct failure class measured separately by BFCL's hallucination category: models omit required parameters or invent parameter names, and a single wrong argument in a multi-step trajectory can move money the planner did not intend ([74]). Human-in-the-loop — the usual fallback — is empirically weak: Anthropic telemetry showed users approved roughly 93% of permission prompts, with the stated cause being approval fatigue as approval volume grows; the company's own guidance is that credential material should never enter the sandbox in the first place, since what is not reachable cannot be exfiltrated ([75]). Agentic safety benchmarks are themselves gameable: one Berkeley RDI study found eight major agent benchmarks exploitable to near-perfect scores without solving any task ([32]).

## Trends and open problems

**Consolidation around protocol, contention around scope.** MCP has become the default integration layer ([10][11]), which shifts research attention from "how do I expose this API" to routing, discovery and schema economics ([42][12][13]). Yet MCP version churn is documented across sources, with different spec versions cited and Sampling marked deprecated in the architecture page ([11]). There is no published head-to-head of retrieval versus lazy schema loading at scale ([13][12]).

**The reliability-versus-autonomy trade is unresolved, and now quantified.** Workflow framing argues for the simplest sufficient structure ([6]); long-horizon data shows the per-step-success tax makes 20-step autonomy fragile ([32][25]). The ethical path suggested by the evidence is that autonomy should be earned by measured per-step reliability and checkpoint design rather than assumed.

**Evaluation validity is the field's most tractable near-term problem.** Contamination on Verified versus decontaminated repos ([51][52]), statistical indistinguishability of top leaderboard entries ([27]), reward-design over/under-estimation up to 100% ([26]), and a reported 37% lab-to-deployment gap ([62]) all point the same direction. Process-level and efficiency metrics (OSWorld-Human's human trajectories ([61]), tau2's error decomposition ([60]), BFCL's cost and latency columns ([18])) are the emerging countermeasures.

**Reward design for agentic RL is genuinely contested.** Dense per-turn rewards can cost up to 14 points ([17]) while format rewards help but intermediate retrieval rewards barely move the needle ([46]); SFT is simultaneously necessary for format and insufficient for generalisation ([47]). Whether RL elicits or creates tool-use competence remains the field's most-cited open theoretical question ([47][36][16]).

**Security will likely be solved architecturally, if at all.** The consensus across the design-pattern, CaMeL and Rule-of-Two lines is a deliberate utility-for-structure trade rather than a defence that preserves full flexibility ([71][72][31]); where model-level defences were tested adaptively they collapsed ([31]), and human approval degrades into rubber-stamping at ~93% approval rates ([75]). The practical research frontier is capability containment with provenance/tainting, egress control and per-call enforcement — the defences that survive adaptive attackers, at a measurable utility cost ([73][69][71]).

**Environment fidelity and evaluation cost are new bottleneck resources.** EnvFactory argues against over-specified synthetic trajectories in favour of fewer verified executable environments ([49]) while VerlTool shows that rollout infrastructure itself determines achievable scale ([48]); meanwhile benchmark sweeps are reported in the tens of thousands of dollars ([62]). Where agents must act on consequential real-world tasks ([57][65]), the gap between affordable evaluation and deployment-relevant risk is widening, not closing.
