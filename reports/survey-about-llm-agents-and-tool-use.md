# LLM Agents and Tool Use: A Survey of Architectures, Training, Evaluation, Protocols and Failure Modes

## TL;DR

- Four paradigms dominate tool-using LLM agents — prompted interleaved reasoning-and-acting (ReAct, which beats imitation and RL baselines by 34% on ALFWorld and 10% on WebShop with one or two in-context examples) [1], self-supervised fine-tuning (Toolformer, which learns which API to call, when, with what arguments) [2], massive-API retrieval-augmented tuning (ToolLLM's 16,464 RapidAPI APIs and Gorilla's RAT, which surpasses GPT-4 at writing API calls) [3][4], and code-as-action, where the model emits a program and a runtime solves it (PAL beats CoT PaLM-540B by 15% top-1 on GSM8K) [5][6].
- Training has visibly shifted from supervised imitation to reinforcement learning with verifiable outcome rewards: ToolRL reports a 17% improvement over base models and 15% over SFT models, with cold-start GRPO beating SFT-then-GRPO, and Search-R1 improves 41% (Qwen2.5-7B) over RAG baselines [7][8][9][10].
- Evaluation is the weakest link: benchmarks saturate at the top (SWE-bench Verified clusters near 81% while SWE-Bench Pro sits near 23% by design) [11][12], the same model can swing ~7 points on GAIA purely from the orchestration harness [13], and LLM-as-judge graders misclassifying 10-15% of trajectories can shift rankings and corrupt RL rewards [14][15].
- The ecosystem has consolidated on two protocols — Anthropic's MCP for agent-to-tool and Google's A2A for agent-to-agent — while their security record is poor: the MCP tool-description field is an unsanitized attack surface [16][8][17], MCP Safety Audit shows LLMs coerced into code execution and credential theft [18], and a public red-teaming competition collected 1.8 million prompt-injection attacks yielding over 60,000 policy violations across 22 agents, with robustness uncorrelated to model capability [19].
- Reliability, not capability, is the binding constraint: failures compound nonlinearly with task length [20][21], long-horizon serving spends up to 62% of execution wall time on synchronous context compaction [22], and production systems report that standard metrics miss four of seven agent-specific failure modes entirely [14].

## Background

An LLM agent, in the sense used throughout this survey, is a language model placed in a loop where it can call external tools — APIs, code interpreters, search engines, robot policies, or other models — observe the results, and continue acting until a task is done. The framing matured quickly. Surveys recast the underlying models as Augmented Language Models, defined by two augmentations: reasoning, meaning decomposing a complex task into subtasks, and tools, meaning calling external modules such as a code interpreter, used either separately or in combination via heuristics or learned from demonstrations [23]. Other surveys give a unified construction framework for LLM-based autonomous agents spanning construction, applications and evaluation [24], and one of the founding tool-learning papers formalizes the loop as understanding the instruction, decomposing a complex task into subtasks, dynamically adjusting the plan through reasoning, and conquering each subtask by selecting appropriate tools — tested with 18 representative tools [25].

Why this matters now is that the interface has escaped the research paper. MCP is described as an open standard for connecting AI applications to external systems, likened to a USB-C port for AI applications and supported by mainstream clients [16]; BFCL v4 re-weighted its leaderboard so that roughly 70% of the score comes from agentic and multi-turn behaviour rather than isolated function calls [26]; and τ-bench's pass^k metric was introduced because an agent that solves a task once may fail it repeatedly [27]. At the same time, deployment has outrun measurement: a synthesis of 27 benchmark, taxonomy and audit papers spanning 19 benchmarks finds progress concentrated in single-turn tool use, short-horizon web navigation and narrowly scoped coding, with failures compounding nonlinearly with task length [20].

## Architectures and Paradigms for Tool Calling

The clearest axis of comparison is where the tool-use competence comes from: the prompt, the weights, or the runtime. ReAct occupies the prompt end, generating reasoning traces and task-specific actions in an interleaved manner so that reasoning induces, tracks and updates action plans while actions query external sources; it requires no fine-tuning and beats imitation and RL methods by 34% on ALFWorld and 10% on WebShop from one or two in-context examples, and reduces hallucination on HotpotQA and Fever through a simple Wikipedia API [1]. PAL sits at the runtime end of the same spectrum by a different route: the LLM decomposes the problem into a program, but the solution step is offloaded to a Python interpreter, motivated by the observation that LLMs make logical and arithmetic mistakes in the solution part even when decomposition is correct; PAL with Codex surpasses chain-of-thought PaLM-540B by 15% absolute top-1 on GSM8K [5]. Code as Policies extends the same idea to embodied control, expressing reactive and waypoint-based robot policies as language model generated programs and using hierarchical code generation that recursively defines undefined functions, which improves the state of the art to 39.8% on HumanEval [6].

Fine-tuning and retrieval form the second family. Toolformer is the canonical self-supervised case: the model is trained to decide which APIs to call, when to call them, what arguments to pass and how to incorporate results into future token prediction, needing only a handful of demonstrations per API, and covering a calculator, a Q&A system, two search engines, a translation system and a calendar [2]; the pipeline keeps a proposed call only if including its result reduces perplexity on the subsequent text beyond a threshold, then fine-tunes the base model on the filtered data [28]. ToolLLM scales the same objective to breadth: 16,464 real RESTful APIs across 49 RapidAPI categories, single- and multi-tool instruction generation, solution-path annotation, a depth-first-search decision-tree algorithm so the model can evaluate multiple reasoning traces, a neural API retriever for the resulting search space, and ToolEval as an automatic evaluator [3]. Gorilla shows that retrieval and tuning compose: a finetuned LLaMA surpasses GPT-4 at writing API calls, and Retriever Aware Training lets it adapt to test-time document changes while substantially mitigating hallucination, evaluated on APIBench [4].

The third family treats the LLM as a controller over a heterogeneous inventory. HuggingGPT is the archetype — ChatGPT performs task planning, selects models by their Hugging Face function descriptions, executes each subtask with the selected model and summarizes the response, with language as a generic interface and the LLM acting as controller over existing AI models [29]. The comparative picture across these families is consistent: prompting is training-free and flexible but bounded by context and the model's prior competence [1]; fine-tuning with retrieval raises call accuracy and suppresses API hallucination at the cost of data pipelines and retraining [4][3]; and code-as-action replaces brittle argument formatting with the exactness of an interpreter, at the price of requiring an execution sandbox and a programmatically expressible action space [5][6].

## Training: From Distillation and SFT to Reinforcement Learning

The training literature reads as a progression in supervision signal. At the self-supervised stage, Toolformer's perplexity-threshold filter requires nothing more than a handful of demonstrations per API, and the base GPT-J-class model is fine-tuned on the calls that survived filtering [2][28]. The instruction-tuning stage made data the bottleneck and then industrialized its production. ToolLLM prompts ChatGPT to generate diverse instructions over its 16,464 APIs, and the resulting ToolLLaMA reaches a 50% pass rate on complex instructions versus 30% for text-davinci-003, matching ChatGPT [30][3]. API-Bank combines a runnable benchmark with a training set of 1,888 tool-use dialogues drawn from 2,138 APIs across 1,000 domains, used to train Lynx from Alpaca; Lynx surpasses Alpaca's tool-utilization performance by more than 26 points and approaches GPT-3.5 [31]. ToolAlpaca attacks the data cost from the other direction, using a multi-agent simulation to synthesize 3,938 tool-use instances from more than 400 real-world APIs spanning 50 categories and fine-tuning 7B and 13B models to generalized tool use comparable to GPT-3.5 on unseen tools [32]. ToolACE-DEV continues the trend by decomposing the task into sub-tasks to reduce reliance on advanced teacher models [33].

The most recent stage replaces imitation with reward. ToolRL frames itself as the first comprehensive study of reward design for tool selection and application within the RL paradigm, using GRPO with a fine-grained reward that decomposes correctness into tool-name, parameter-name and parameter-value matching, reporting a 17% improvement over base models and a 15% gain over SFT models, and arguing that SFT struggles to generalize to unfamiliar or complex tool scenarios [7]; secondary summaries of the same paper describe that reward as decomposing correctness into tool names, parameter names and parameter content [8][9]. Those summaries also report that reward granularity matters — accuracy degrades monotonically as the reward is coarsened toward a single exact-match indicator — and that cold-start GRPO beats SFT-then-GRPO (46.42% versus 52.98% on Qwen2.5-3B), with Qwen2.5-7B-Instruct rising from 41.97% to 58.38% on BFCL [8][9]. Search-R1 generalizes the recipe to retrieval, training the model purely with RL to emit multiple search queries during step-by-step reasoning with real-time retrieval, using retrieved-token masking for stability and a simple outcome reward, improving 41% (Qwen2.5-7B) and 20% (Qwen2.5-3B) over RAG baselines on seven QA datasets [10]. SWE-Gym carries the approach into real software engineering, providing 2,438 real Python task instances with executable runtimes and unit tests, and yielding up to 19% absolute gains in resolve rate and 32.0%/26.0% on SWE-Bench Verified/Lite for open-weight agents [34]. Preference optimization appears as a lighter-weight complement: DPO optimizes RL-like objectives without reward models, and one project reports 94.1% schema accuracy on Llama-2-7B with LoRA for deciding when to call an API versus generate text [35]. The recurring reported pattern is that outcome- or verifier-grounded RL generalizes better than SFT alone [7][9][10].

## Evaluation: Benchmarks, Saturation and Unreliable Measurement

Agent evaluation is layered, and each layer has a characteristic failure. At the API-call layer, API-Bank offers a runnable environment of 73 API tools with 314 annotated tool-use dialogues and 753 API calls, separating the abilities to call a known API, to retrieve then call, and to plan multi-step API use when tools are unknown upfront [31][36]. BFCL uses roughly 2,000 question-function-answer pairs across 18 categories and introduces AST-based evaluation that parses the call and compares it structurally to ground truth, with categories for simple, multiple, parallel, nested and irrelevant calls; a documented finding is that models often choose the right function but pass wrong or hallucinated arguments, so one should expect 15-25% lower scores on argument correctness than on function selection, and BFCL explicitly does not test whether the function actually executes successfully [37]. The benchmark's own weighting has shifted with the field: in BFCL v4, Agentic is 40% of the score, Multi-Turn 30%, Hallucination 10% and the classic Live and Non-Live function-calling categories only 10% each [26].

Interactive benchmarks expose the gap between single-shot accuracy and dependable behaviour. GAIA contains 466 questions in three difficulty tiers with unambiguous answers; at launch in late 2023 GPT-4 with plugins scored 15% against 92% for humans, and the best agent now reported is at 74.6% [13]. WebArena's 812 self-hosted web tasks are graded by functional success with no partial credit — humans score about 78%, first-generation agents about 14%, and the current top agent 71.6% overall but only 59.2% on shopping versus 86.0% on a Reddit-style task [13]. τ-bench simulates multi-turn customer service with a simulated user, backend tools and a policy document across retail (115 tasks) and airline (50 tasks), grading the final database state; GPT-4o solved close to 61% of retail tasks on a single try but fewer than a quarter of tasks across eight consecutive attempts, which is precisely why pass^k was introduced [27]. SWE-bench grades patches against the tests of the human fix: Agentic progress ran from 12.47% with SWE-agent v1 in 2024 to ~50% in early 2025 and a leaderboard compressed within 1-2 points near 81% by March 2026 [11]. ToolBench, meanwhile, became a de facto standard for tool-augmented reasoning, with one fine-tuned small model reporting a 77.55% pass rate against ChatGPT-CoT at 26.00%, ToolLLaMA-DFS 30.18% and ToolLLaMA-CoT 16.27% [38].

The mature critical literature argues these numbers are weaker evidence than they appear. SWE-Bench Pro was built explicitly to address four limitations — data contamination, limited task diversity, oversimplified problems, and unreliable or irreproducible testing — sourcing tasks from diverse complex codebases and holding part of the evaluation private, and its top scores sit near 23% against roughly 79-81% on SWE-bench Verified [12][11]. The harness matters as much as the model: the same Claude Opus 4 scores 64.9% on GAIA inside the Princeton HAL agent but only 57.6% inside Hugging Face's Open Deep Research framework, and GAIA scores across systems span 44.8% to 92.36% on the same tasks [13]. Graders are a separate threat surface — a benchmark of 931 human-annotated mobile-agent trajectories over 6 benchmarks, 4 agent models and 68 apps evaluates 6 judge methods and notes that a judge misclassifying even 10-15% of trajectories can shift agent rankings substantially and that judge errors used as RL reward directly corrupt learning [14]. The first comprehensive survey of LLM-based agent evaluation analyzes benchmarks across core capabilities (planning, tool use, self-reflection, memory), application-specific and generalist benchmarks, benchmark dimensions and evaluation frameworks, and identifies critical gaps in cost-efficiency, safety and robustness together with a need for fine-grained, scalable evaluation [39]; a complementary argument holds that aggregate-score leaderboards fail to capture deployment-relevant dimensions and show rank instability, motivating frameworks based on predictive validity and out-of-distribution criteria [15]. τ²-bench illustrates the same compression, with leading models now clearing close to 87.9-90% on its text tasks [27].

## Orchestration, Multi-Agent Systems and the Protocol Layer

As tool inventories grew, the research problem shifted from calling one tool to selecting and coordinating many, and the ecosystem standardized the interface in parallel. MCP, released by Anthropic in November 2024, defines a host/client/server architecture over JSON-RPC 2.0 in which the host spins up a dedicated client per server, with servers exposing three primitives: tools that the model invokes, resources that provide context data, and prompts as reusable templates [40][16]. Google's A2A, announced 9 April 2025 with more than 50 technology partners, targets agent-to-agent interoperability instead — client and remote agents exchange task-oriented messages, capabilities are advertised via a JSON Agent Card, long-running tasks have a lifecycle and emit artifacts, and the transport builds on HTTP, SSE and JSON-RPC with OpenAPI-parity authentication and a secure-by-default principle; Google explicitly frames A2A as complementing MCP rather than replacing it, an assessment echoed by coverage noting MCP had already become the de facto standard for connecting agents to external systems [41][42].

Coordination research converges on structure. Surveys model LLM-based multi-agent systems through their communication topology, including a communication-centric survey that examines scalability and security challenges [43], and newer work generates topologies dynamically: TopoDIM, a decentralized framework that one-shot generates heterogeneous communication topologies, reports reducing token consumption by 46.41% while improving performance by 1.50% [44]. Hierarchical planner-plus-executor designs recur, with AgentOrchestra improving general-purpose task solving through modular collaboration and intelligent tool management and outperforming flat-agent and monolithic systems [45], and OrgAgent organizing a multi-agent system like a company with governance, execution and compliance layers to cut token consumption relative to flat collaboration [46]. Scaling to large tool libraries has become a retrieval problem: ScaleMCP integrates MCP servers with a tool retriever and embedding strategy for dynamic selection [47], Tool-to-Agent Retrieval embeds tools and agents in a shared vector space for 19.4% Recall@5 and 17.7% nDCG@5 gains [48], Graph RAG-Tool Fusion combines vector retrieval with graph traversal to capture tool dependencies on ToolLinkOS [49], and HYSET argues retrieval should be set-level, formulating it as hyperedge prediction on a co-invocation hypergraph so candidate tool sets are evaluated jointly rather than one tool at a time [50].

That standardization has imported a security surface. The MCP tool-description field is an unsanitized attack surface: a malicious or compromised server can embed arbitrary instructions in what appears to be help text that agents follow without user awareness, and high-severity vulnerabilities through mid-2026 showed leading IDEs auto-executing project-defined MCP servers with developer-level OS privileges and no process isolation [17]. Simon Willison documented rug pulls and tool shadowing, tool-poisoning prompt injection, and exfiltration of WhatsApp history via whatsapp-mcp, concluding that mixing tools with untrusted instructions is inherently dangerous [51]. MCP Safety Audit demonstrates that industry-leading LLMs can be coerced into using MCP tools to compromise a developer's system through malicious code execution, remote access control and credential theft, and introduces MCPSafetyScanner, the first agentic tool for assessing an arbitrary MCP server [18]. The MCP landscape survey decomposes the server lifecycle into four phases and 16 activities and builds a taxonomy of 16 threat scenarios across four attacker types [52]; MCP Security Bench evaluates vulnerability across tool discovery, invocation and response handling [53]; and ToolHijacker showed prompt injection that manipulates tool selection by inserting malicious tools into the library [54]. At the systems level, a survey of confidential computing for agentic AI notes that agents accumulate sensitive context, hold credentials and delegate via MCP and A2A, enabling prompt injection, context exfiltration, credential theft and inter-agent message poisoning [55], while APPA treats information-flow control as a recoverable policy-governed mechanism rather than an abort-only barrier against confused-deputy attacks and exfiltration [56].

## Applications, Limitations and Open Problems

Deployment evidence is concentrated exactly where the failure analysis predicts it should be. The 27-paper synthesis finds substantial progress in single-turn tool use, short-horizon web navigation and narrowly scoped coding, and simultaneously reports that failures compound nonlinearly with task length, that strong sub-task performance does not reliably translate into end-to-end success, and that additional scaffolding does not consistently improve reliability; it clusters failures into tool invocation and parameter errors, planning and constraint-satisfaction failures, long-horizon degradation from context accumulation, multi-agent coordination failures, safety and security failures, and measurement validity problems [20]. A cross-domain diagnostic benchmark makes the horizon effect concrete: HORIZON collected over 3,100 trajectories across four agentic domains with GPT-5 and Claude variants and found that even a small per-step error rate compounds across dependent steps, driving agents from reliable short-task performance to near-systematic failure at longer horizons [21]. Serving-side measurements locate a mechanistically distinct bottleneck: synchronous context compaction dominates wall time at low thresholds, consuming up to 62% of total execution on HotpotQA, and reasoning quality degrades well before the context window is reached because the model must attend over an increasingly long, low-signal history [22].

Production evidence is harsher than benchmark evidence. A production evaluation study grounded in systems operating at billion-event scale offers a taxonomy of seven agent-specific failure modes covering compounding decision errors, tool failure cascades, non-deterministic output drift and the absence of ground truth for long-horizon tasks, and finds that standard metrics such as ROUGE, BERTScore, accuracy/AUC and benchmarks like HELM, MT-Bench, AgentBench and BIG-bench fail to detect four of the seven failure modes entirely while detecting the other three only after a lag of multiple evaluation cycles [14]. Harness engineering analysis reaches a compatible conclusion from the systems side: real-world agent reliability is often constrained less by the base model than by the execution harness around it — environment, tools, context, orchestration, observability, evaluation and governance — and compositional security properties that prove an agent, harness and environment satisfy a safety specification remain unsolved, with current defenses reactive rather than preventive [57].

Security is the sharpest open problem, and the evidence is quantitative. A public red-teaming competition targeting 22 frontier agents across 44 realistic deployment scenarios collected 1.8 million prompt-injection attacks, with over 60,000 successfully eliciting policy violations such as unauthorized data access, illicit financial actions and regulatory noncompliance; nearly all agents exhibited policy violations for most behaviours within 10-100 queries, and robustness showed only limited correlation with model size, capability or inference-time compute [19]. Surveys document more than thirty attack techniques spanning input manipulation, model compromise, system and privacy attacks and protocol-level vulnerabilities, including prompt-to-SQL injections and the Toxic Agent Flow exploit in GitHub MCP servers, and observe that the growth of plugins, connectors and inter-agent protocols has outpaced security practices, producing brittle integrations built on ad-hoc authentication, inconsistent schemas and weak validation [58]. An IEEE Access survey proposes a taxonomy spanning prompt injection and jailbreaks, autonomous cyber-exploitation and tool abuse, multi-agent and protocol-level threats, interface and environment risks, and governance and autonomy concerns, arguing that agents' ability to act autonomously across web, software and physical environments creates risks distinct from both traditional AI safety and conventional software security [59]. A peer-reviewed review synthesizing 45 sources, industry security reports and documented real-world exploits names the "lethal trifecta" of privileged access, untrusted input and ability to share data publicly, and concludes that perfect security may be unachievable, so practice should adopt defense-in-depth to limit damage from inevitable breaches [60].

Read together, the trajectory suggests three convergent directions. First, evaluation must become longitudinal, deployment-linked and resistant to contamination, since saturation at the top of Verified-style leaderboards coexists with ~23% on contamination-hardened successors and with rank instability on aggregate scores [11][12][15], and since harness-induced variance and grader error can each exceed the differences between the models being compared [13][14]. Second, the reliability frontier is moving from model capability to system engineering — verifier-based inference-time scaling and executable environments for training, dynamic topology and tool retrieval for coordination, and compaction-aware serving for long horizons [34][44][50][22] — which also explains why better base models do not automatically yield better agents [57][20]. Third, safety needs structural rather than filter-based defenses, because the attack surface is the tool interface itself [17][51][18][52][53][54] and because robustness is not a by-product of capability [19][60]; recoverable information-flow control and confidential-computing designs are early attempts to make that structural claim [56][55], and the open question is whether such guarantees can be composed across the MCP and A2A layers that agents now routinely cross [58][59].
